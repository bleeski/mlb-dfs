# 2026-10-06 DEV (Session 117, R434): a late swap carries no sleeve or seat stamps, so an authorized sleeve entry can lose its team silently

**Observed.** `grep -nE "sleeve|tail_team|stack_sleeve" tools/late_swap.py mlb_engine/swap/late_swap_manager.py` returns nothing. `late_swap_manager.build_entry_requirements` (`:455-465`) writes no `tail_team`, `stack_sleeve_team` or `stack_sleeve_min`, and the swap's bank carries no sleeve tags, so `contest_allocator._resolve_classic_sleeves` returns `no_sleeve_bank` for it (the status, not a refusal). `inherit_swap_controls` (`tools/late_swap.py:909-935`) carries scalar controls only, and a stamp is not a control (R268(a)). So an entry R434 seated on a named secondary stack (or R422 on a tail team, or R406 in a world) that a swap AUTHORIZES is re-solved freely: if the named team's hitters sit in open (unlocked) slots, the re-solve is free to replace them and the lineup can end with the team below `min`, with no line saying so. Entries the swap does not authorize, and slots whose game has started, are protected byte for byte as before.

**What was and was not verified.** Read off the code and the grep above, and off the keys `build_entry_requirements` writes. NOT run on a live swap: no parent run with a sleeve seat exists on this host (R434 landed in this session), and a scratch re-solve through `select_and_assign_entries` would only restate the code reading.

**What R434 left for this.** The tracked delivery record's `extra.stack_sleeve` carries `team_by_entry` and the outcome `seated: {entry_id: team}`, so a swap session can read which entry held which team. `tools/late_swap.py` already reads the parent's delivery record for its label (`parent_delivery_label`), which is the seam.

**Decided 2026-10-06** (Ben took the architect's recommendation; CHANGELOG `Decided, not yet built: a late swap holds an operator-named stack, and only that`): hold the OPERATOR-NAMED stack (R434), not the derived sleeves (R406 worlds, R422 tail seats), relaxed and counted when it cannot be kept, never a refusal, with a report-only printout of the named team's hitter count before and after as the first step. The reading below is the build, and the question it closes was "whether a swap should HOLD a strategy preference at all".

**Candidate item.** For an authorized entry whose parent record names a stack seat, stamp the same `stack_sleeve_team`/`stack_sleeve_min` on its swap entry requirement and give the swap's bank the named-stack jobs (`build_sleeve_jobs`'s `named_stack` branch is depth-only and cheap), so the mask holds the team through the swap; when it cannot, relax and count it in the swap's brief like any S control. The R406 weighted sleeves and R422 tail seats have the same hole and the same seam, so one item can close the class. F-3 never relaxes; a locked slot is never moved.
