# 2026-10-06 DEV (Session 115, R428): the swap's first bank slice purges the build's stored jobs in the shared cache file, before and after R428

**Observed.** `late_swap.py` keys its bank cache `runs/bank_cache_<date>_<pool_signature>.json`, the same file the build uses for that slate. `bank_cache.projection_digest` hashes EVERY column of every row (`bank_cache.py:621-651`), and a swap's frame differs from its build's by at least `Notes`, the batting orders and F2, `Excluded` and, since R428, the carried cells. So the swap's first `extend_bank` reports `superseded_jobs_dropped` and retires the build's indexed bank in the shared file (`drop_stale_jobs` retires jobs the index places under another digest; they are saved as `retired_jobs` and filtered out of the merged candidates). The R428 session's premise run re-read 33 `initial_build` frames from 2026-09-01/02/08 and found 0 equal to any digest in their date's cache index, so an enriched swap frame would never have matched the build's either.

**Why it is filed and not fixed.** It is the same before and after R428 (the swap was already cold: R428 changes the frame's values, not whether the digest matches), it is the R101 design (a digest mismatch fails closed), and the bank is not R428's to change. The cost shows only when a BUILD wants its own stored bank back after a swap on the same slate: a rebuild then starts from the retired set.

**Candidate item.** Either give the swap its own cache file (`bank_cache_<date>_<sig>_swap.json`, so the build's file is never touched), or keep the file shared and have the swap restore retired jobs it did not build when it exits. Measure first: how often a build follows a swap on one slate (re-promotion after a repair, a rebuild after a scratch), and how long the cold bank costs on a 10-game slate. S-M; touches `bank_cache.py` and `late_swap.py` (the cache path at `cache_path = REPO / "runs" / ...`), so it needs PROBE.

Nothing here is a lift, an edge, an ROI or a win rate.
